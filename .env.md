# .env.md — running jev-traderbot live on Monad mainnet

Everything below is derived from the code in `src/config.ts`, `src/market.ts`,
`src/chain.ts`, `src/trader.ts` and `src/model.ts`. Where a value is hardcoded
and **cannot** be set from `.env`, it says so explicitly.

> **Read this first.** Live mode posts a real post-only order **every block**
> (~3 blocks/second on Monad) and Monad charges gas on the **gas limit**, not on
> gas used, whether the order lands or reverts. At the default settings that is
> roughly **0.036–0.044 MON per block**, i.e. **~430–530 MON per hour** at the
> 100 gwei base-fee floor. Run dry first, and start live with the smallest size
> the market allows.

---

## 0. TL;DR — minimal live `.env`

```dotenv
# --- network ---
RPC_URL=https://your-dedicated-monad-rpc
READ_RPC_URL=https://your-dedicated-monad-rpc
WS_URL=wss://your-dedicated-monad-rpc

# --- wallet: this is what makes it live ---
PRIVATE_KEY=0x<64 hex chars, no spaces>
DRY_RUN=false

# --- model ---
MODEL=mock                      # or jev / minara — see §8
# TYPESAFE_AI_API_KEY=...       # MODEL=jev
# MINARA_API_KEY=...            # MODEL=minara

# --- market (must match the margin account) ---
MARKET=0x40c49F171202F91ff5d2faE34c22dD2BFdD22aF0
MARGIN_ACCOUNT=0x2A68ba1833cDf93fa9Da1EEbd7F46242aD8E90c5

# --- money ---
TRADE_SIZE_BASE=0.000125        # smallest legal order on cbBTC-USDC
QUOTE_INSIDE_TICKS=1
MAX_POSITION_BASE=0.000125      # one order max while you smoke-test
MARGIN_BASE=0.000125
MARGIN_QUOTE=50
BANKROLL_USD=50

# --- gas ---
MAX_FEE_GWEI=400
PRIORITY_FEE_GWEI=2
# GAS_LIMIT=                   # leave empty: estimated once at startup

PORT=3000
```

Then:

```bash
chmod 600 .env
bun run start
curl -s localhost:3000/ | jq '{model, wallet, dryRun, pair}'
```

You want `"dryRun": false` and `"wallet": "0x…"` before you trust anything else.

## 1. How the bot decides it is "live"

One line, `src/config.ts:13`:

```ts
dryRun: env("DRY_RUN") === "true" || !env("PRIVATE_KEY")
```

Therefore:

| `PRIVATE_KEY` | `DRY_RUN` | Result |
|---|---|---|
| unset/empty | anything | **dry run** (nothing is signed or sent) |
| set | `true` | **dry run** (key ignored) |
| set | `false`, empty, or unset | **live** |

Live means `new ethers.Wallet(PRIVATE_KEY)` is created at startup, and every block
signs and broadcasts a type-2 `batchUpdate` transaction to `MARKET`.

`DRY_RUN=false` is the explicit form; you may also delete `DRY_RUN` while keeping
the key, but writing `false` is safer because it survives an accidental copy of
the example file.

## 2. Variable reference (grouped)

### 2.1 Network — required for live

| Variable | Live value | Notes |
|---|---|---|
| `RPC_URL` | dedicated HTTPS provider | Sends, receipts, nonce, one-time `eth_estimateGas`. Public `rpc.monad.xyz` works but is shared. |
| `READ_RPC_URL` | dedicated HTTPS provider | Every block: one `getL2Book` `eth_call`, one `eth_getLogs` poll, and `eth_blockNumber` every 150 ms. The public RPC caps at ~25 rps; live traffic plus a dashboard can brush that limit (you will see `rpc http 429`). |
| `WS_URL` | `wss://…` or empty | Optional `newHeads` subscription for lower block latency. If empty or the socket drops, the 150 ms polling backstop keeps the loop alive. |

`chainId` is **hardcoded to 143** (`src/config.ts:8`). There is no env override.

### 2.2 Wallet — required for live

| Variable | Value | Notes |
|---|---|---|
| `PRIVATE_KEY` | `0x` + 64 hex | Use a **fresh hot wallet**, not your main wallet. The bot keeps a **local nonce counter**; any other transaction sent from the same address (manual, another bot, a second instance) will race it. One key, one instance. |
| `DRY_RUN` | `false` | See §1. |

### 2.3 Market — required, must be a matched pair

| Variable | Default | Notes |
|---|---|---|
| `MARKET` | Kuru cbBTC-USDC order book | The order book the bot trades. Its params (decimals, tick, min/max size) are fetched on-chain at startup. |
| `MARGIN_ACCOUNT` | `0x2A68…90c5` | Kuru `MarginAccount` that this market settles against. **Only change it together with `MARKET`.** The default pair is documented as verified (`verifiedMarket(market) == true`). A mismatch means deposits and orders go to the wrong account and every order reverts. |

If you change markets you must also re-derive:

1. `MARGIN_ACCOUNT` (slot 73 of the new OrderBook proxy),
2. `TRADE_SIZE_BASE` within the new market's `minSize`/`maxSize`,
3. `QUOTE_INSIDE_TICKS` relative to the new tick size,
4. `MARGIN_BASE` / `MARGIN_QUOTE` in the new tokens.

**Hard live prerequisite that has nothing to do with `.env`:** the book must have
**both a bid and an ask** at the block the bot reads. `src/book.ts:210` throws
`empty book side at block N (bids=0 asks=1)` otherwise, the block is skipped, and
on the current cbBTC-USDC market that is exactly what happens today (verified via
the Kuru SDK as well as the raw RPC). A live run against a one-sided book will
start cleanly, deposit margin, and then trade **nothing**.

### 2.4 Money and sizing

| Variable | Default | Meaning |
|---|---|---|
| `TRADE_SIZE_BASE` | `0.01` | Size of **every** order, in the base asset. Must be ≥ the market's `minSize` and ≤ `maxSize`. On cbBTC-USDC: min `0.000125` cbBTC, tick `0.01` USDC. At a ~87,900 USDC cbBTC price, `0.01` cbBTC is ~879 USDC — size by notional, not by the default. |
| `QUOTE_INSIDE_TICKS` | `1` | The quote is placed this many ticks inside the touch (bid + N ticks, ask − N ticks). It never crosses: if the spread is too tight it clamps to the touch. `0` joins the best bid/ask. |
| `MAX_POSITION_BASE` | `0.05` | Absolute exposure cap, counting the position **plus resting orders plus in-flight sends**. If a side would breach it, the bot posts the other side (`capped: true`) or nothing. |
| `BANKROLL_USD` | `5000` | Display only: denominator for `totals.pnlPct`. Does not affect sizing or risk. |
| `HORIZON_BLOCKS` | `100` | The question the model answers ("higher or lower after N blocks"). ~300 ms per block → 100 ≈ 30 s. Only the model sees it. |

### 2.5 Margin deposits — required for any order to be possible

Kuru limit orders draw from the **margin account**, not the wallet. At startup
`ensureMargin()` (`src/market.ts:229`) tops the margin balance up to these
targets, and only deposits what the wallet actually holds:

| Variable | Default | Notes |
|---|---|---|
| `MARGIN_BASE` | `0.1` | Target base-asset balance in margin. Needed for **asks** (selling). |
| `MARGIN_QUOTE` | `2000` | Target quote-asset balance in margin. Needed for **bids** (buying). |

Deposit mechanics, for each token:

1. If margin already holds ≥ target → nothing happens.
2. Otherwise the bot computes `want − have`, then:
   - **native MON** (base of a MON market): sent as tx `value` with `deposit(...)`;
   - **ERC20** (cbBTC, USDC, …): `approve(marginAccount, MaxUint256)` once, then `deposit(...)`;
3. If the wallet holds **less** than the shortfall, it logs a warning and deposits
   the whole wallet balance instead.
4. If the wallet holds **zero**, it deposits nothing and the bot runs with that
   side unfunded — bids or asks (or both) will then be blocked, and the loop will
   either quote only the other side or not at all.

The bot does **not** withdraw from the margin account. Your funds stay there
until you withdraw them through Kuru.

**Wallet balances you need before the first live run**

For the default cbBTC-USDC market:

| Asset | Purpose | Minimum |
|---|---|---|
| MON | gas (charged per block, on the limit) | see §3; fund several hours of runway |
| cbBTC (`0xd18B…414b`) | `MARGIN_BASE` + a buffer | `MARGIN_BASE` |
| USDC (`0x7547…b603`) | `MARGIN_QUOTE` + a buffer | `MARGIN_QUOTE` |

The bot never swaps assets for you. If you fund only USDC, it can only bid; if
only cbBTC, it can only ask.

### 2.6 Gas — required, with a cost trap

| Variable | Default | Notes |
|---|---|---|
| `GAS_LIMIT` | empty | Empty → one `eth_estimateGas` **at startup** (needs margin funds) for a place with no cancels, `+90,000`, `×1.15`. If estimation fails, falls back to a hardcoded `350000`. Set it explicitly once you know your number. It is **never** estimated in the loop. |
| `MAX_FEE_GWEI` | `400` | Type-2 fee **cap**. Effective price = base fee + priority, so the cap only costs money if the base fee actually rises. |
| `PRIORITY_FEE_GWEI` | `2` | Monad hardcodes `eth_maxPriorityFeePerGas` at 2 gwei; the bot sends static fees and never queries them in the loop. |

Cost math (Monad charges the **limit**):

```
per block  = GAS_LIMIT × (base + priority)
           ≈ 350,000 × 102 gwei         = 0.0357 MON   (fallback limit, floor fee)
           ≈ 427,800 × 102 gwei         = 0.0436 MON   (typical estimated limit)
per hour   = per block × 12,000 blocks  ≈ 428 – 523 MON
worst case = 350,000 × 402 gwei         = 0.1407 MON/block ≈ 1,688 MON/hour
```

Cancels are batched into the same transaction, and a reverted transaction still
costs the limit. This is the dominant live cost — not slippage.

### 2.7 Model

| Variable | Values | Notes |
|---|---|---|
| `MODEL` | `mock` \| `jev` \| `minara` | `mock` = deterministic momentum heuristic (no key, ~80 ms). `jev` = TypeSafe AI evaluation model. `minara` = Minara Agent API adapter added for the Kairos migration. |
| `TYPESAFE_AI_API_KEY` | required for `MODEL=jev` | Without it the bot warns and silently falls back to the mock. |
| `JEV_MODEL_ID` | `jev-latest` | Model id passed to TypeSafe. |
| `MINARA_API_KEY` | required for `MODEL=minara` | Pro/Partner subscription; keys are suspended on downgrade. Missing key → warning + mock fallback. |
| `MINARA_BASE_URL` | `https://api.minara.ai` | `https://api-developer.minara.ai` also appears in Minara's docs. Overridable so tests can point at a local mock. |
| `MINARA_MODE` | `fast` | Never `expert` in the loop: expert is for analysis and is not latency-compatible. |
| `MINARA_BLOCK_DEADLINE_MS` | `250` | Hard `AbortController` timeout, 50 ms below the ~300 ms block. A late call is a **hold** (no order) — or a cached decision with `late: true` if one is fresh (≤ `MINARA_CACHE_MAX_BLOCKS`, spread not doubled). |
| `MINARA_CACHE_MAX_BLOCKS` | `3` | Max age of a reusable last-known-good decision. `0` disables the cache. |

There is no env for the Jev/Minara retry policy: the adapter never retries inside
a block, by design.

### 2.8 Server / dashboard

| Variable | Default | Notes |
|---|---|---|
| `PORT` | `3000` | Bun server: `GET /` snapshot, `GET /history`, `GET /events` SSE, `POST /stop`, `POST /start`. Bind it to localhost or firewall it — `/stop` and `/start` are unauthenticated. |

Hardcoded, not settable: `pendingBlocks = 10` (give up on a receipt after 10
blocks), `refreshBlocks = 200` (re-read gas price, margin balances, vault state),
`historySize = 1000`, `chainId = 143`, `gasLimitFallback = 350_000`.

## 3. Step-by-step: from zero to a live order

### Step 1 — Create and fund a hot wallet

- Generate a fresh key; never reuse your main wallet.
- Send **MON** for gas (several hundred MON for a multi-hour run at defaults).
- Send **base asset** (cbBTC) and **quote asset** (USDC) for `MARGIN_BASE` /
  `MARGIN_QUOTE`.
- If the wallet holds native MON as the *base* asset of some other market, that
  MON also serves as the margin deposit (sent as tx value).

### Step 2 — Choose RPC endpoints

- One provider for sends/receipts, one for reads. The same provider is fine if it
  is dedicated; the public endpoint is acceptable only for a short smoke test.
- `WS_URL` must speak `wss://` and support `eth_subscribe` with `newHeads`. If
  unsure, leave it empty — polling alone works.

### Step 3 — Confirm the market and margin account

- Leave the defaults **only** for Kuru cbBTC-USDC.
- For any other market, pair the correct `MARGIN_ACCOUNT`, and re-check
  `minSize`, `tickSize`, and token decimals from the on-chain market params.
- Remember the two-sided-book requirement (§2.3). A live bot on a one-sided book
  is a gas-free no-op, but it will still hold margin deposits.

### Step 4 — Size the trade

- Set `TRADE_SIZE_BASE` inside `[minSize, maxSize]`.
- Set `MAX_POSITION_BASE` ≥ `TRADE_SIZE_BASE`, ideally a small multiple.
- Set `MARGIN_BASE` ≥ a few × `TRADE_SIZE_BASE` for asks and
  `MARGIN_QUOTE` ≥ a few × `TRADE_SIZE_BASE × price` for bids. Otherwise the cap
  flips the quote to the other side or suppresses it.

### Step 5 — Decide gas policy

- Leave `GAS_LIMIT` empty for the first run; read the startup log line
  `gas limit … ~X MON per block` and then pin it.
- Keep `MAX_FEE_GWEI=400` (cap, not cost) unless you know the base fee moves.
- Keep `PRIORITY_FEE_GWEI=2` (Monad's fixed priority).

### Step 6 — Pick the model

- `MODEL=mock` for the first live run: it isolates plumbing, gas, margin and
  order placement from model latency/cost.
- `MODEL=jev` needs `TYPESAFE_AI_API_KEY`.
- `MODEL=minara` needs `MINARA_API_KEY` **and** a market that trades frequently
  enough that the 250 ms budget is realistic.

### Step 7 — Write `.env`, lock permissions, start

```bash
cp .env.example .env
$EDITOR .env
chmod 600 .env
bun run start
```

Bun loads `.env` automatically. `.env` is gitignored — keep it that way.

### Step 8 — Verify the startup log

You should see, in order:

```
jev-trader · model=… · cbBTC/USDC · … · wallet 0x… · market 0x… · read https://… · :3000
margin · 0.000125 cbBTC · 50.00 USDC
gas limit 427800 · maxFee 400 gwei · priority 2 gwei · ~0.0436 MON per block, ~523 MON per hour
```

`DRY RUN` must be **absent** from the first line. If you see
`gas estimate failed`, the bot will use the 350k fallback — usually because the
margin account has no funds yet.

### Step 9 — Verify the snapshot

```bash
curl -s localhost:3000/ | jq '{model, wallet, dryRun, pair, latest}'
```

- `dryRun: false`, `wallet` = your address.
- `latest: null` means no block has produced a decision yet. If it stays null
  while blocks advance, check the log for `empty book side` or RPC errors.

### Step 10 — Arm the kill switch before you need it

```bash
curl -X POST localhost:3000/stop     # pause: no reads, no model calls, no orders
curl -X POST localhost:3000/start    # resume
```

`/stop` leaves the server, block feed and dashboard up; in-flight sends still
settle. Know this command before the first live block.

## 4. Operational realities you should plan for

1. **Every block is an order.** There is no "only when the edge is big enough"
   throttle. Gas is the strategy's main cost.
2. **Receipts arrive late.** Sends are fire-and-forget; `placed`/`reverted`/`lost`
   land on later blocks. A `lost` quote re-syncs the nonce from
   `max(latest, pending)`.
3. **The position cap can override the model.** The event keeps the model's
   probabilities but the quote may be on the other side (`capped: true`) or
   absent.
4. **Margin funds gate the side.** Bids need quote, asks need base; a side
   without funds is never quoted.
5. **Dry run is not a rehearsal of your balances.** It never touches the key,
   margin, or gas. The first live block is the real test.
6. **The dashboard is read-only** (`ui/`, `web/`). It cannot place or cancel
   orders. Only `MARKET`/`MARGIN_ACCOUNT` and restarting the process move money.

## 6. Preflight checklist

- [ ] Wallet is fresh, funded with gas MON + base + quote, key stored only in `.env` (mode 600).
- [ ] `DRY_RUN=false`, `PRIVATE_KEY` set, no trailing spaces/newlines inside the key value.
- [ ] `RPC_URL` / `READ_RPC_URL` are dedicated and respond (`eth_blockNumber`).
- [ ] `MARKET` + `MARGIN_ACCOUNT` are the verified pair; margin account funded or fundable.
- [ ] `TRADE_SIZE_BASE` within `[minSize, maxSize]`; `MAX_POSITION_BASE` ≥ it.
- [ ] `MARGIN_BASE`/`MARGIN_QUOTE` ≥ several orders per side.
- [ ] Gas runway covers hours, not minutes (`~430–530 MON/hour` at defaults).
- [ ] Market has a two-sided book; otherwise the bot will idle.
- [ ] Model key present for the chosen `MODEL`; lateness policy understood.
- [ ] `POST /stop` known and reachable; `PORT` not exposed to the internet.
- [ ] No other process uses the same key (nonce races).

## 7. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Snapshot still `"dryRun": true` | `DRY_RUN=true` or empty `PRIVATE_KEY` | §1 |
| `empty book side at block N` every block | one-sided market or wrong `MARKET` | Use a market with bids **and** asks |
| `rpc http 429` | public RPC rate limit (reads + logs + polling) | Dedicated `READ_RPC_URL` |
| `nonce too low` loop | another tx from the same address, or a second bot instance | One key, one instance; the bot re-syncs on failure |
| `gas estimate failed … using 350000` | no margin funds at startup | Fund the margin account or set `GAS_LIMIT` |
| Quotes only on one side, `capped: true` | `MAX_POSITION_BASE` or margin funds on that side | Raise the cap or fund both tokens |
| `Minara HTTP 401` / `minaraFailures` climbing | bad/expired `MINARA_API_KEY` or no Pro/Partner plan | Rotate key or use `jev`/`mock` |
| `Minara HTTP 409` | reused `requestId` (duplicate request) | Should not happen: ids are per-process+block; restart the process |
| `Minara: content is not JSON` | model answered free-form | Treated as failure by design; check the model/prompt |
| `EADDRINUSE :3000` | another bot/dashboard on the port | Set `PORT` or stop the other process |
| Bot runs, no events, no errors | `latest` stays null because books are one-sided | Expected; see §2.3 |

## 8. Security and hygiene

- `.env` holds a spending key. `chmod 600`, never commit it, never paste it into
  a dashboard, issue tracker, or chat.
- Keep only the funds the bot needs in the hot wallet; withdraw margin proceeds
  from Kuru when you stop.
- `/stop` and `/start` have no auth: bind `PORT` to localhost or put it behind a
  proxy with auth.
- Dry run and live share the same process: a stray `PRIVATE_KEY` in your shell
  environment (exported earlier) can flip a run live even if `.env` is clean.
  Check `env | grep PRIVATE_KEY` before starting.
